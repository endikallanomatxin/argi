# C interoperability

C interoperability uses typed declarations, explicit C-compatible representations,
and the target's C ABI. Ordinary Argi wrappers adapt foreign resources, buffers,
errors, and cleanup to the language's normal contracts.

## Functions and symbols

A `CFunction` declaration without a body imports an external symbol:

```rg
abs(.value: CInt) -> (.result: CInt) : CFunction

_abs(.value: CInt) -> (.result: CInt)
    : CFunction(.symbol = "abs")
```

The symbol defaults to the declaration's name. `.symbol` selects another linker
name without changing the Argi name or module visibility. Input names are local
binding information; C receives arguments in declaration order.

A declaration with a body implements a function with C ABI. Publication is
explicit and independent of the calling convention:

```rg
add(.left: CInt, .right: CInt) -> (.result: CInt)
    : CFunction(.export = true, .symbol = "argi_add") := {
    result = left + right
}
```

`.export = true` publishes the symbol; `.symbol` is optional here too. A body
without export can provide a C-compatible callback. Export does not change
Argi's module visibility rules. Each published C symbol has one concrete
signature; Argi multiple dispatch does not overload a linker symbol.

A C signature has zero or one output. A returned struct is one typed output;
additional results use explicit pointer parameters. The compiler lowers
arguments and results according to the target ABI, including any required
register splitting or indirect return storage. The number of Argi output
fields does not select an ABI return convention.

## Foreign-call capability

Calling a foreign function requires access to a
`$&ForeignFunctionInterface` capability. The conventional dependency name is
`ffi`, supplied through the normal lexical `assume` and transitive `reach`
mechanisms:

```rg
main(.system: System) -> (.status_code: Int32 = 0) := {
    assume ffi ::= system.ffi
    value := abs(-42)
}
```

The capability is a checked Argi dependency, separate from the foreign
signature. It is not emitted as an extra C argument. Failure to supply it is a
compilation error. Wrappers may accept it as an ordinary Argi argument.
Authorization does not certify pointer bounds, resource effects, or the foreign
implementation's behavior.

Entering an exported function from C does not create a `System` or grant ambient
capabilities. An export that needs resources must obtain them through an explicit
context established by its host. A raw context address alone does not establish
validity or authorization. The same obligation applies to callbacks invoked by C.

## C-compatible types

Only types with a defined C representation may cross the ABI boundary by value.
Target-dependent scalar types such as `CInt` and `CLong` describe their C
counterparts; fixed-width integers and floating-point types can be used where
the external signature has matching representations.

C-compatible structs preserve the target's C field layout, padding, and
alignment:

```rg
Coordinates : CStruct = (
    .horizontal: Float64
    .vertical: Float64
)

Number : CUnion = (
    .integer: CInt
    .real: Float64
)

Status : CEnum = (
    ..ok = 0
    ..invalid = 3
)
```

`CUnion` fields share storage. Reading the appropriate field remains the
binding's responsibility; it does not have the discriminator of an Argi choice.
`CEnum` variants have no payloads and may declare explicit numeric values. Its
integer representation must match the external declaration.

Ordinary struct layout is not a C ABI guarantee. Arrays within records require
compatible element representations and C layout. `String`, `ArrayView`,
`Virtual`, and ordinary errable results require wrappers rather than being
passed as their Argi representations. Generic declarations must resolve to
concrete compatible signatures before crossing the boundary.

## Pointers and resources

`RawPointer#(.t: T)` represents a C pointer at the ABI boundary, not an Argi
record passed by value. It may contain a null address and does not establish
bounds, alignment, initializedness, or lifetime. An external pointer does not
become a safe `&T` or `$&T` merely because its declared pointee type is `T`.

Wrappers use `ArrayView` or `ArrayViewRO` for bounded buffers and lower them to
raw pointer/length parameters. C strings use explicit helpers from
`core/strings/c_strings.rg`. Foreign handles and their allocation/free pairing
remain explicit; cleanup can be provided by ordinary Argi `deinit` wrappers.
Reference construction must satisfy the [safety model](34_safety_model.md) and
[allocation contracts](35_allocation.md).

Headers do not reveal whether a call retains a pointer, frees storage, invalidates
views, or initializes a destination. The binding must establish these contracts;
the capability and C ABI compatibility checks do not infer them. Wrappers translate
C status codes into Argi errors, and exports translate Argi errors into explicit
C-compatible results instead of propagating them across the foreign boundary.

## Headers and linking

[Named header imports](02_modules.md#c-interoperability) produce the same typed
bindings as manual declarations. Include paths, defines, and target options
participate in translation and cache identity. Imported declarations do not
prove safety contracts or grant capabilities.

Library selection, search paths, and static/shared linking belong to build
configuration. A symbol name identifies the declaration to resolve; a header
import does not implicitly download or select a library to link.

> [!IMPLEMENTATION]
> The compiler currently accepts plain `CFunction` as an alias of
> `ExternFunction`, with direct external calls, ordinal `Int32` C enums, and
> C-union storage. Options, exports, foreign-call capability enforcement,
> `CStruct`, target C scalar types, raw-pointer ABI adaptation, and header imports
> are not implemented. Existing low-level libc declarations still use references
> or native integers for several foreign pointer signatures. Aggregate call
> lowering is not a general C ABI implementation.
