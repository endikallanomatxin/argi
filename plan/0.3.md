# 0.3

## Release purpose

Make Argi more useful for everyday programs on top of the 0.2 safety foundation.
Improve expression and error ergonomics, add small core utilities, and develop
minimal system services that support real command-line and library consumers.
More modules should exercise these foundations rather than grow independently
of their dependencies.

Goals:

- Close specific language/safety gaps and improve everyday ergonomics.
- Expand core with text/numeric utilities and practical system capabilities.
- Develop more modules backed by usable core services.
- Improve build and editor workflows through measured compiler reuse.

## Development order and scope

1. Address language/safety gaps and small utilities first: float parsing,
   deterministic random generation, and semantic versioning. Add Deque only
   when a queue consumer justifies it.
2. Scope time and process services independently. Keep system entropy separate
   from deterministic random state, then establish a networking baseline.
3. Build URI/HTTP support after their dependencies are usable. Develop linear
   algebra around a concrete storage/dimension use case before BLAS interop.
4. Pursue compiler reuse and formatting alongside these steps when they do not
   depend on unsettled language design. Performance refactors need measurements.

Select a bounded set of milestones from this sequence before expanding the
release. Close the release when that set works end to end, has appropriate
coverage, and leaves no unresolved correctness gaps in the supported paths;
remaining candidates move forward rather than delay publication indefinitely.
Runtime/concurrency, GPU, and broader ownership/representation changes belong
in [0.4](0.4.md).

Remove completed tasks after validation. Keep language contracts in
`description/`, and useful unfinished examples near their library modules.

## Compiler, language, and tooling

### Language features

#### Expressions and functions

- [ ] Define scalar grouping without ambiguity with single-field values and
  settle richer pipe/arithmetic precedence. Existing arithmetic tiers and
  value-construction parentheses are specified in
  `description/00_syntax_overview.md`.

- [ ] Specify ordinary integer widening and explicit conversions before
  implementing them. Library utilities must not emulate numeric conversion
  through pointer reinterpretation.

- [ ] Extend pipes to multiple placeholders, placeholders inside expressions,
  builtin calls, and qualified/generic calls only with settled precedence and
  evaluation-order rules.

#### Initialization and virtual types

- [ ] Track destination places reached through pointer parameters during direct
  calls to fallible initializers. Preserve outcome-sensitive initializedness;
  retain the current rejection where the destination is not visible to safety.

- [ ] Evaluate virtual conversion for fully bound associated-parameter abstracts
  when a concrete use case requires it. Signature admissibility is specified
  in `description/134_virtual_types.md`; keep the dedicated diagnostic for
  unsupported conversions.

#### Error ergonomics

- [ ] Evaluate `Errable`-specific `handle` sugar for consuming a local error
  into a final value. Keep it over ordinary `match error.reason`, require the
  shared result slot on every handled path, and preserve existing block and
  return semantics.

### Compiler and safety follow-up

#### P1: Runtime diagnostics

- [ ] Define useful runtime safety failure diagnostics beyond a bare trap.
  Coordinate compiler-generated behavior with the library error contracts.

#### P2: Conditional performance and maintenance

These investigations need representative measurements or an actual change
that exposes a useful boundary; they are not release gates.

- [ ] Share summary traversals or invalidate dimensions selectively only if
  repeated traversal remains significant. Verify cross-dimension dependencies.
- [ ] Consider checkpoint/rollback or partial COW only if profiling shows state
  copying dominates transactional call checking.
- [ ] Consider versioned virtual-summary caches only if dispatch merging
  dominates. Invalidate successful and unrepresentable merges when concrete
  implementation summaries change.
- [ ] Separate global resolution/scheduling from diagnostic construction when
  changes expose a useful boundary; file size alone does not justify splitting.
- [ ] Evaluate optimization of proven allocator alignment checks in generated
  LLVM IR without weakening checks whose obligations remain dynamic.

### Tooling

- [ ] Establish native Windows x64 support for the compiler and implemented
  core library, following [the Windows support plan](windows_support.md).
  Validate one toolchain first and review scope before making it a release gate.
- [ ] Measure in-memory module reuse before designing a persistent cache;
  follow [the incremental compilation experiment](incremental_compilation.md).
  Reuse the proven boundary for incremental LSP diagnostics where useful.
- [ ] Implement basic source formatting for supported syntax.
- [ ] Define explicit build target selection and validate each supported host
  or target adapter. Existing `--release`, `--output`, and artifact emission
  are implemented; add further controls only for concrete needs.

## Core library

Library contracts belong in `description/`; [the core overview](../core/core.md)
distinguishes implemented modules from sketches. Choose core versus more
placement deliberately, and scope each service independently.

### P1: Everyday utilities

- [ ] Define float parsing grammar, rounding, overflow, and locale independence
  before implementation; evaluate formatting gaps against `format.rg`.
- [ ] Implement a deterministic seedable PRNG with reproducible sequences,
  unbiased bounded sampling, and explicit non-cryptographic status. Keep
  system entropy separate; evaluate core versus `more/math/random` placement.
- [ ] Implement semantic-version parse/compare/format with prerelease precedence,
  build metadata, invalid input, and explicit ownership of textual pieces.
  Decide whether this tooling utility belongs in core or more.
- [ ] Evaluate a growable `Deque<T>` for a concrete queue consumer, preserving
  growth failure and owning-element relocation within the existing owner model.

### P2: System services

- [ ] Implement duration arithmetic, monotonic instant differences, wall-clock
  timestamps, and sleep through explicit capabilities. Specify units, overflow,
  clock origin, interruption, and validated platform adapters. Leave calendars
  and time zones for later.
- [ ] Implement process spawn/wait, exit status, explicit stream ownership, and
  termination. Specify arguments/environment, handle and failure cleanup, and
  validate claimed hosts. Do not make shell strings the only spawning API.
- [ ] Define system-entropy access and failure independently of PRNG state.
  Cryptographic randomness needs its own quality contract; existing sketches
  do not establish that guarantee.
- [ ] Implement a scoped networking baseline: address resolution, TCP/UDP,
  socket ownership, partial I/O, errors, and platform validation. Reuse stream
  contracts and defer higher protocols until this baseline is usable.

## More library

### Application and domain libraries

- [ ] Implement URI parsing/building with explicit ownership and formatting
  when a consumer needs it.
- [ ] Build HTTP/1 request/response and client/server baselines after networking
  and stream primitives are usable. HTTP belongs in more.
- [ ] Develop vectors/matrices with explicit storage and dimension contracts.
  Exercise compile-time dimension compatibility through generics and abstracts
  where supported, separately from dynamic-dimension runtime checks. Preserve
  expressive goals and examples in `more/math/linear_algebra/`.
- [ ] Add BLAS interop only for a concrete linear-algebra implementation after
  layout, linking, foreign-call capability, and type boundaries are settled.
