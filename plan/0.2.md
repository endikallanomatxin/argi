# 0.2

Goals:

- Define and implement useful language features.
- Grow the bundled library beyond its current foundations.
- Develop a few `more/` modules for real programs.
- Improve compiler reliability and tooling ergonomics.

Work is grouped below into compiler/language/tooling and core/more libraries.
Priorities guide implementation order; exploratory and conditional items are
not promises that every candidate will ship in 0.2. Remove completed tasks
after validation. Keep language contracts in `description/`, and preserve
useful unfinished examples near their library modules.

## Compiler, language, and tooling

### Prioritized compiler and safety follow-up

Priorities reflect correctness, language-contract clarity, and implementation
dependencies. Conditional investigations do not imply confirmed bugs or a
commitment to a proposed implementation.

#### P1: Arithmetic and diagnostic gaps found during validation

- [ ] Report unsatisfied generic function constraints at call sites. An
  unsupported owning-element `reverse` currently reports a missing function
  instead of identifying the `ImplicitlyCopyable` requirement.

- [ ] Define scalar grouping syntax without ambiguity with single-field
  values, and settle richer pipe/arithmetic precedence. Arithmetic now has
  conventional multiplicative/additive tiers with left associativity;
  parentheses still construct values. See `description/00_syntax_overview.md`.

- [ ] Diagnose incompatible numeric binding types during semantizing rather
  than reaching codegen `InvalidType`. Ordinary integer widening/conversion
  needs an explicit language contract; library utilities must not emulate it
  through pointer reinterpretation.

#### Future spatial safety extensions

Reassess these design candidates when a concrete use case requires them.
The supported bounded-storage contracts and trusted proof obligations belong
in [the safety model](../description/34_safety_model.md) and
[allocation](../description/35_allocation.md).

- [ ] Design a general slot-owner API for ordinary initialization, borrowing,
  extraction, replacement, and cleanup. Repeated selection or copying of a
  `MaybeUninit<T>` handle does not establish exclusive authority. Validate
  owner-private occupancy, initialization failure, owning values, duplicate
  handles, and outstanding references before exposing reads. Prefer existing
  moves and generation invalidation over compiler tracking of arbitrary slot
  addresses.
- [ ] Evaluate certified bounded suballocation and external range import beyond
  the validated allocator/collection path. Specify which obligations are
  checked at runtime and which remain trusted. Ordinary `&T` certifies one
  object; adjacent selection must start from a bounded owner/region/view.
  Do not extend unbounded trusted offsets or reinterpretation with general
  pointer-arithmetic proofs.

#### P2: Targeted performance work

- [ ] If repeated summary traversals remain significant, share traversal or
  invalidate dimensions selectively with explicit dependency tracking. Verify
  cross-dimension dependencies before skipping recomputation.

- [ ] Consider checkpoint/rollback or partial COW only if representative
  profiling shows state copying dominates transactional call checking.
- [ ] Consider versioned virtual-summary caches only if merged dispatch
  summaries dominate representative workloads. Preserve invalidation when
  implementation summaries change, including cached unrepresentable merges.

#### P3: Maintenance and platform confidence

- [ ] Consider separating global resolution/scheduling from diagnostic
  construction when changes expose a useful boundary. Large file size alone
  does not justify splitting `global/semantizer.zig` or `codegen.zig`.

### Language features

- 📝 Fallible in-place `init`
  - 💭 Track destination places reached through pointer parameters during
    direct calls to fallible initializers

- 📝 Advanced polymorphism
  - 📝 virtual types
    - [ ] Evaluate implementing virtual conversion for fully bound
      associated-parameter abstracts when a concrete use case requires it.
      Signature admissibility is specified in `description/134_virtual_types.md`;
      unsupported parameterized conversion now has a dedicated diagnostic.
    - [ ] Decide whether a stable foreign virtual ABI is needed; if so, specify
      slot ordering and external table construction independently of LLVM
      layout. The current two-pointer handle alone is not an ABI guarantee.

- 📝 Advanced functions
  - 📝 richer pipe operator with multiple placeholders
  - 📝 placeholders inside more complex expressions
  - 📝 builtins in richer pipe chains
  - 📝 qualified/generic pipe cases with settled precedence
  - 💭 closure model

- 📝 Module-level runtime initialization
  - 💭 non-constant top-level bindings
  - 💭 cross-file ordering semantics for folder modules
  - 💭 decide whether imported modules may run implicit runtime initialization
  - 💭 0.1 explicitly does not implement implicit init-on-import; keep current diagnostics until this is designed properly

- 📝 Error ergonomics
  - 💭 `Errable`-specific `handle` sugar for consuming a local `Errable` into a final value
  - 💭 keep it as sugar over ordinary `match error.reason { ... }`
  - 💭 do not introduce value-returning blocks or new `return` semantics for this
  - 💭 require the shared result slot to be assigned on every handled error path

- 💭 More advanced comptime. keep it minimal and only when it unlocks a
structural compiler/build-system need
  - 💭 evaluate shared compile-time execution and interactive tooling in
    `plan/comptime_execution.md`

- 💭 Decide whether function inlining and loop unrolling need language-level
  controls. If in-place initialization later accepts uninitialized storage,
  define its safety rule explicitly rather than treating inlining as proof.

- 💭 Threading

- 💭 Define an async runtime and concurrency model, using Zig as an
  architectural reference.

## Core and more libraries

P1 is immediate work; P2 is the next set of candidates. Later work needs an
explicit scope decision or a demonstrated use case before implementation.
Library contracts belong in `description/`; [the core overview](../core/core.md)
describes implemented modules and distinguishes them from sketches.

### P1: Everyday text

- [ ] Define float parsing grammar, rounding, overflow, and locale independence
  before implementation; evaluate formatting gaps against existing `format.rg`.

### P2: Collection extensions

- [ ] Evaluate a growable `Deque<T>` after a concrete queue use case; keep growth
  failure and owning-element relocation within the established owner model.

### P3: Small utilities and system services

These are independently scoped candidates, not a requirement to implement the
whole OS surface before the release.

- [ ] Define and implement a deterministic seedable PRNG with reproducible
  sequences, unbiased bounded sampling, and explicit non-cryptographic status.
  Choose core versus `more/math/random` placement deliberately; its current
  file is empty. Keep system entropy a separate capability.
- [ ] Define system-entropy access and failure behavior independently of PRNG
  state. Cryptographic randomness needs its own quality contract; existing
  `more/crypto/random` sketches do not supply that guarantee.
- [ ] Implement semantic-version parse/compare/format, including prerelease
  precedence, build metadata, invalid input, and ownership of textual pieces.
  Decide whether this tooling-oriented utility belongs in core or more.
- [ ] Implement minimal time services: duration arithmetic, monotonic instant
  differences, wall-clock timestamps, and sleep through explicit capabilities.
  Specify units, overflow, clock origin, interruption behavior, and supported
  platform adapters. Leave calendars and time zones outside this baseline.
- [ ] Implement a process baseline: spawn, wait, exit status, explicit stream
  ownership, and termination. Define argument/environment passing, handle
  cleanup and failure cleanup; validate each claimed host platform. Avoid a
  shell-string API as the only spawning interface.
- [ ] Define useful runtime safety failure diagnostics beyond a bare trap.
  Coordinate any compiler-generated behavior with the compiler checklist.
- [ ] Evaluate establishing allocator metadata in-place before publishing
  references; current private trusted helpers retain their obligations.

### Later core and language-dependent candidates

- [ ] Define consuming iteration only with a concrete ownership use case.
  `TransferIterable`, `for ~ item`, move-taking indexed places, and allocator-
  aware value copies are separate possible designs, not accepted syntax.
  Record language decisions in the compiler checklist before implementation.
- [ ] Implement a minimal networking capability only when scoped: address
  resolution and TCP/UDP operations, socket ownership, partial I/O, errors,
  and platform validation. Reuse stream contracts where appropriate.
- [ ] Evaluate atomics, OS threads, synchronization, and runtime integration in
  that dependency order when concurrency work begins. Choose memory-order
  and ownership contracts before exposing provisional APIs.
- [ ] Reassess compact/packed choice storage using an actual compiler/library
  workload before extracting a generic collection.
- [ ] Reassess packed arrays, linked lists, ropes, SoA, and strided or
  multidimensional views only with representative use cases. General slot-owner
  APIs and certified external regions remain future spatial extensions in the
  compiler checklist; they are not prerequisites for every library task here.

### More library candidates

- [ ] Implement a URI parsing/building baseline with explicit ownership and
  formatting rules when a consumer needs it.
- [ ] Build HTTP/1 request/response and client/server baselines after usable
  networking and stream primitives exist; HTTP belongs in more.
- [ ] Develop vectors/matrices with explicit storage and dimension contracts.
  Exercise compile-time compatible dimensions through generics and abstract
  contracts where supported; distinguish dynamic-dimension runtime checks.
  Preserve the examples and expressive goals in `more/math/linear_algebra/`.
- [ ] Add BLAS interop only after layout, linking, foreign-call capability, and
  type boundaries are settled for a concrete linear-algebra implementation.

### Deliberately deferred scope

Graphs, GPU/parallelism, broad public platform APIs, advanced reflection,
calendar/time-zone systems, debug binary formats, and a programmable build
system remain exploratory inventory in `core/library_ideas.txt` and their
existing sketches. They are not immediate library milestones for 0.2.
