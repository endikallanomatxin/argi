# 0.4

## Release purpose

Extend Argi beyond the practical programming baseline of [0.3](0.3.md), toward
concurrent execution and heavier application domains. Define execution,
ownership, and platform contracts before growing the runtime or exposing
specialized library APIs. GPU and advanced protocols build on those contracts.

Goals:

- Develop a coherent concurrency/runtime model with explicit lifetime rules.
- Extend core with the primitives and collections needed by actual consumers.
- Enable heavier protocol, GPU, and numerical work in more.
- Evaluate advanced language/tooling designs where they unlock those uses.

## Development order and scope

1. Choose a concrete execution use case and settle its ownership/platform
   boundaries. Develop atomics, OS threads, and synchronization before async
   task/runtime integration.
2. Add specialized storage and language extensions only where that use case
   requires them. General slot owners, external regions, closures, and foreign
   virtual ABI work are independent design candidates, not shared prerequisites.
3. Extend more protocols after the networking/HTTP baseline. Scope GPU and
   heavier numerical work after their execution/storage contracts are usable.
4. Evaluate package tooling and shared comptime/interactive execution against
   concrete needs; do not require a new VM or JIT to deliver the runtime work.

This is a direction for later development, not a commitment to every candidate
below. Select and validate an end-to-end milestone before fixing the release
scope; carry independent experiments forward instead of coupling their closure.
Keep accepted language decisions in `description/` and remove completed tasks.

## Compiler, language, and tooling

### Ownership and spatial extensions

The current bounded-storage contracts and trusted obligations remain in
`description/34_safety_model.md` and `description/35_allocation.md`.

- [ ] Design a general slot-owner API for initialization, borrowing, extraction,
  replacement, and cleanup. A copied `MaybeUninit<T>` handle does not establish
  exclusive authority. Validate owner-private occupancy, initialization failure,
  owning values, duplicate handles, and outstanding references. Prefer existing
  moves and generations over tracking arbitrary slot addresses in the compiler.
- [ ] Evaluate certified bounded suballocation and external range import for a
  concrete consumer beyond the allocator/collection path. Specify runtime checks
  and trusted obligations. Ordinary `&T` certifies one object; adjacent selection
  must start from a bounded owner/region/view, not unbounded pointer arithmetic.
- [ ] Design consuming iteration only for a concrete ownership use case.
  `TransferIterable`, `for ~ item`, move-taking indexed places, and allocator-
  aware copies are separate proposals, not accepted syntax.

### Language features and execution

- [ ] Define a closure model with explicit capture, ownership, and lifetime rules.
- [ ] Decide module-level runtime initialization: non-constant top-level values,
  cross-file order, and whether imports may trigger initialization. Preserve
  current diagnostics until the ordering and lifetime model is specified.
- [ ] Decide whether a stable foreign virtual ABI is needed. If so, specify slot
  order and external table construction independently of LLVM layout; a
  two-pointer handle alone is not an ABI guarantee.
- [ ] Evaluate shared comptime execution and interactive tooling using
  [the execution experiment](comptime_execution.md). Reuse existing semantics
  before committing to another IR, VM, REPL, or JIT architecture.
- [ ] Decide whether inlining and unrolling need language controls. If in-place
  initialization accepts uninitialized storage, define its safety independently
  of optimization.
- [ ] Develop concurrency in dependency order: atomics, OS thread handles,
  synchronization, then async runtime/task integration. Specify memory ordering,
  ownership, cancellation, and cleanup before exposing provisional APIs.
- [ ] Explore a GPU programming model only with a concrete workload and explicit
  platform, memory, and execution boundaries.

### Tooling and platforms

- [ ] Evaluate package management after package identity, versioning, dependency
  resolution, and build inputs have clear contracts.
- [ ] Evaluate an `audit` tool for misuse patterns and capability/reach usage
  after defining checks that add value beyond compiler diagnostics.
- [ ] Extend the platform/target model beyond the validated 0.3 baseline only for
  concrete consumers; avoid a broad public platform API without a use case.

## Core library

### Specialized collections and memory

- [ ] Reassess compact/packed choice storage with an actual compiler/library
  workload before extracting a generic collection.
- [ ] Reassess packed arrays, linked lists, ropes, SoA, and strided or
  multidimensional views with representative consumers.
- [ ] Evaluate establishing allocator metadata in-place before publishing
  references; current private trusted helpers retain their proof obligations.

### Concurrency support

Implement library primitives alongside the compiler/runtime contracts above:
atomics, OS thread handles, and synchronization before async runtime integration.

## More library

### Protocols and heavier domains

- [ ] Add HTTP/2, WebSockets, or RPC after networking and HTTP/1 baselines are
  usable. Scope protocol, client, and server support independently.
- [ ] Develop GPU utilities and heavier numerical/scientific libraries only
  after their execution, storage, and interoperability contracts are settled.

## Unscheduled exploration

Graphs, broad platform APIs, advanced reflection, calendars/time zones, debug
binary formats, and a programmable build system remain unscheduled exploratory
inventory in `core/library_ideas.txt` and existing sketches. Revisit them when
needed rather than making their completion a release gate.
