# 0.5 — Resource authority foundations

The immediate priority is a small, compositional safety model, not broader
scheduling support. The proposed rules and implementation gate are in
[the resource authority core](resource_authority.md). The
[concurrency research](concurrency.md) and
[virtual execution investigation](virtual_execution_safety.md) retain the design
history and concrete compiler gaps.

The current native backend supports plain results and checked nonowning loans.
It does not yet transfer general owners or guarantee ordinary-memory race freedom.
Keep sequential mutable aliasing, two-pointer Virtual handles and conservative
call-entry authorization. Ownership, access authority and operation execution
requirements are distinct; access footprints do not certify synchronization.

## Development gates

1. **Formalize and consolidate the core.** Explain loans, transfer, retention,
   erasure, completion and protected access with one requirement model. Define
   result-to-input resource relations and their instance bindings. Map them to
   existing safety summaries rather than introducing another effect system. Keep
   may-access bounds; a general ordered-effect representation is not required.
   [Associated contract projections](contract_members.md) now use unary region
   members, without expanding concurrency permissions. Multiple-participant
   projections remain a separate semantic extension.
2. **Close confirmed soundness gaps.** Prioritize unknown virtual/indirect/native
   accesses and the provenance of native task buffers. Do not infer containment
   from lifetime or exempt a library by name. Native assumptions need a small,
   audited boundary; Argi implementations must prove their contracts. Callback
   signatures now preserve checked access bounds through indirect calls; this
   does not close the separate unknown-call authorization gate.
3. **Demonstrate complete owner transfer.** Start with a known destructor without
   external resources, then retain a borrowed dependency, then a virtual
   deallocator. Preserve responsibility, authority and cleanup through success,
   failure, discard and opaque storage, using the existing executor.
4. **Demonstrate verified sharing.** A mutex owns protected storage and grants
   scoped authority through a guard. Earlier outside aliases cannot bypass it;
   guard-derived references become unusable before release. Exclusion and memory
   publication must have certified runtime implementations.
5. **Validate composition and ergonomics.** Repeat those cases through generic
   calls, contracts, Virtual and collections. Measure compilation costs and check
   that ordinary callers do not need to manage region annotations. Prefer common
   certified contracts or rejection when heterogeneous extraction loses evidence.

Advance beyond these gates only if shared references, owner transfer with external
cleanup, and a mutex can be explained by the same rules. Dynamic conformances
remain a later option, not the basis of the model.

## Later work

Certified partitioning, channels, task groups, backend-independent waiting,
cancellation, worker pools, serialized/local executors and green threads remain
valuable directions. They are not simultaneous requirements for 0.5. Keep their
protocols compatible with the core without implementing them all now.

System.executor integration still requires native-only virtual methods to coexist
with System-based VM and compile-time execution. Resolve that implementation
constraint without bypassing safety.

Unscheduled: explicit closure captures, module runtime initialization,
slot-owner/suballocation APIs and additional platforms. Other topics have their
own notes in this directory.
